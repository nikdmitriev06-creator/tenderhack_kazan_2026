# Разбор ТЗ: требования, ограничения, вопросы

Первоисточники: [01-case-page.md](01-case-page.md) (задачи Т1–Т8) и [02-polozhenie.md](02-polozhenie.md) (пункты
Положения). Всё, что ниже без ссылки на пункт, — наша интерпретация, её можно оспорить.

## 1. Суть кейса одной фразой

Поставщик вводит описание товара свободным текстом. Система предлагает унифицированные характеристики из
справочника КТРУ (и датасета организаторов), приводит значения и единицы к единому виду, по шагам сужает
категорию КТРУ до конечного кода и объясняет каждую найденную ошибку.

Почему это больно порталу, видно на живой карточке: [../research/zakupki-portal.md](../research/zakupki-portal.md).
Коротко: в карточке СТЕ нет кода КТРУ, половина характеристик из описания не попала в структуру, а штатный подбор
СПГЗ отнёс белую офисную бумагу к позиции для цветной. С июня 2026 портал заполняет характеристики по фото; наше
решение работает по тексту описания и дополняет эту функцию
([../research/tenderhack-patterns.md](../research/tenderhack-patterns.md#8-куда-движется-портал)).

## 3. Чек-лист требований

Статус: ☐ — не начато. Колонка «Чем докажем» — то, что жюри должно увидеть глазами.

| № | Требование (источник) | Как закрываем | Чем докажем |
|---|---|---|---|
| Т1 | Изучить данные организаторов | EDA: объёмы, категории, разнобой ключей характеристик, инвентарь единиц, пропуски | отчёт о качестве данных с цифрами «нашли N проблем» |
| Т2.1 | По описанию товара определить подходящие характеристики | описание → кандидаты категорий КТРУ (гибридный поиск: BM25 + эмбеддинги) → шаблон характеристик выбранной позиции | форма заполняется из текста, у каждого значения видно, из какого куска текста оно взято |
| Т2.2 | Сопоставить значения и единицы измерения | парсер «число + единица», справочник ОКЕИ, конвертация (мм/см/м, г/кг, мл/л), диапазоны вида «>=80 … <90», синонимы значений | таблица «было → стало» с единицей и правилом |
| Т2.3 | Привести к унифицированному виду | канонические имена характеристик: «Толщина, мкм» → «Толщина» + «мкм»; синонимы ключей («Плотность, г/м2» = «Масса бумаги площадью 1м2») | до/после на реальных СТЕ из датасета |
| Т2.4 | Поэтапно сужать категории КТРУ до конечного кода по вводимым характеристикам | множество кандидатов + фильтр по введённым значениям + «следующий лучший вопрос» (характеристика с максимальным приростом информации) | счётчик «осталось N кодов» в интерфейсе, дерево сужения |
| Т2.5 | Если КТРУ однозначно не определить — уведомить и предложить конкретные шаги | ответ «уточните X: варианты a/b/c, это отсечёт k кодов» | сценарий демо с неоднозначным товаром |
| Т3 | Распознавать и исправлять ошибки: опечатки, явные несоответствия, несуществующие значения — с указанием и обоснованием | опечатки: расстояние редактирования до допустимых значений и раскладка; несуществующие: значения вне списка КТРУ; несоответствия: единица не того типа, число вне правдоподобного диапазона, противоречие названию или описанию; официальные правила модерации портала (не меньше 4 характеристик, единица отдельно, значение не повторяет название, в названии нет значения и единицы) | панель проблем: где ошибка, какое правило нарушено, чем исправить, кнопка «применить» |
| М | Сценарии «пользователь должен иметь возможность …» из методички (выдадут на старте) | разложить в чек-лист в первый час и проверять демо по нему | каждый сценарий показан в демо |
| Т4 | Удобный и понятный веб-интерфейс | SPA на React: ввод описания, живая форма характеристик, панель сужения КТРУ, панель ошибок, пакетная загрузка | живое демо |
| Т5 | Протестировать на реальных кейсах, включая неполные и некорректные данные | золотой набор из датасета: скрываем часть характеристик и проверяем восстановление; вносим искусственные ошибки и меряем обнаружение | таблица метрик (раздел 6) и прогон одной командой |
| Т6 | Предусмотреть масштабирование | stateless API, очередь RabbitMQ и воркеры для пакетных задач, кэш Redis, Postgres + pgvector (HNSW), модели за Ollama | схема и замер пропускной способности |
| Т7 | Продемонстрировать работоспособность | 3–4 сценария демо: чистый, с опечаткой, неоднозначный КТРУ, недопустимое значение | прогон в `docker compose up` |
| Т8 | Схема реализации в нотации BPMN | BPMN 2.0 (`docs/bpmn/*.bpmn`, открывается в bpmn.io / Camunda Modeler) и PNG | файл в репозитории |
| П7.7 | Представить «математическую модель» | формулы: скоринг кандидатов КТРУ, критерий выбора следующего вопроса, правила и пороги детектора ошибок | `docs/math-model.md`, ссылки из интерфейса («почему так») |
| П8.4 | Без работоспособного проекта 1 место не присуждают | стабильная сборка, демо без интернета | прогон на чистой машине до 13:00 11.10 |

## 4. Ограничения из Положения

- **п. 6.4 — победителям прошлых хакатонов ДКП повторная регистрация запрещена.** Команду могут дисквалифицировать
  на любом этапе. По новости mos.ru (mos.ru/news/item/175830073) TenderHack в Нижнем Новгороде 2026 выиграла
  команда «Наши любимые MISIS-Mojarung». До старта выяснить, кого из состава это касается, и при необходимости
  уточнить у организаторов.
- **п. 7.5 — проект целиком создаётся на хакатоне.** До 21:00 09.10 в репозитории только общий каркас (инфраструктура,
  health-проверки, сборка) и документы. Доменная логика (КТРУ, характеристики, ошибки) — только после старта.
  Топ-5 проходят код-ревью, история коммитов видна.
- **п. 6.17 — данные организаторов нельзя публиковать и передавать третьим лицам.** Датасеты не коммитим (`data/`
  в `.gitignore`), репозиторий приватный. Отправка данных во внешний облачный LLM-API — тоже передача третьим лицам,
  поэтому модели локальные (Ollama).
- **п. 6.19 — своя техника.** Модели должны влезать в ноутбуки команды или в доступный нам GPU-сервер.
- **п. 7.4 — Open Source разрешён.** Библиотеки и открытые веса можно.
- **п. 7.7 — формат защиты: презентация, математическая модель, демонстрация прототипа «посредством онлайн
  платформы».** Что за платформа — спросить.
- **п. 1.7, 7.11 — правила могут поменять.** Перечитать перед стартом.

Ограничения, которые почти наверняка придут в методичке на старте (дословно одинаковые во всех четырёх методичках
2026 года):

- решение работает на Linux и даёт веб-интерфейс;
- **полный запрет любых внешних API**, включая LLM (OpenAI, Gemini, Claude и т.п.) и поисковики: всё крутится на
  серверах команды;
- запрет low-code и no-code;
- открытые модели можно, но **необоснованно тяжёлые снижают оценку**; предпочтение лёгким с быстрым инференсом.

## 5. Вопросы организаторам (в чат или на старте)

1. Кого из команды касается п. 6.4 (победители НН 2026) и можно ли участвовать.
2. Данные: формат и объём датасета СТЕ; какой справочник КТРУ (выгрузка ЕИС с характеристиками и допустимыми
   значениями? версия, даты применения?); будет ли скрытый тестовый набор.
3. Критерии и веса: придут в методичке на старте — сверить с гипотезой из
   [../research/tenderhack-patterns.md](../research/tenderhack-patterns.md#2-критерии-по-городам-100-баллов-за-этап).
4. Есть ли интернет на площадке (для скачивания моделей и образов; внешние API в решении всё равно запрещены).
5. Демо на нашей технике или на их стенде; что за «онлайн платформа» из п. 7.7.
6. Формат сдачи: дедлайн 13:00 11.10 — это пуш в репозиторий? Какой доступ дать жюри к приватному репозиторию?
7. Нужны ли на выходе, кроме кода КТРУ, ОКПД2, КПГЗ и СПГЗ.

## 6. Метрики (для Т5 и математической модели)

| Метрика | Что меряет |
|---|---|
| Accuracy@1 и @5 кода КТРУ | точность итогового кода и попадание в топ-5 кандидатов |
| Среднее число шагов сужения | сколько вопросов до конечного кода |
| Precision / Recall заполнения характеристик | по скрытым характеристикам золотого набора |
| Доля верно нормализованных единиц | по размеченной выборке |
| Precision / Recall / F1 детектора ошибок | на искусственно испорченных СТЕ (опечатка, чужая единица, значение вне списка, противоречие) |
| Латентность p95, пропускная способность | онлайн-запрос и пакетная обработка |

## 7. Глоссарий

- **СТЕ** — стандартная товарная единица: карточка товара в каталоге Портала поставщиков (наименование, модель,
  производитель, категория КПГЗ, характеристики, единица ОКЕИ, страна ОКСМ, ссылки на КТРУ и СПГЗ, оферты).
- **КТРУ** — каталог товаров, работ, услуг для государственных и муниципальных нужд (ЕИС, zakupki.gov.ru).
  Код строится от ОКПД2, у позиции есть характеристики с допустимыми значениями и единицами.
- **ОКПД2** — общероссийский классификатор продукции по видам экономической деятельности.
- **КПГЗ** — московский классификатор предметов государственного заказа (ЕАИСТ); иерархический код вида
  01.15.01.01.01.
- **СПГЗ** — московский справочник предметов государственного заказа: конкретные позиции под КПГЗ со своими
  характеристиками и допустимыми значениями.
- **ОКЕИ / ОКСМ** — классификаторы единиц измерения и стран мира.
- **Оферта** — предложение поставщика (цена, регион) к СТЕ.
- **Котировочная сессия** — процедура закупки малого объёма на портале.

## 8. Как кейс ложится на каркас

| Компонент каркаса | Роль в решении |
|---|---|
| `api` (FastAPI) | онлайн-запросы интерфейса: разбор описания, сужение КТРУ, проверка характеристик |
| `worker` (FastStream + RabbitMQ) | пакетные задачи: проверка загруженного файла СТЕ, построение индексов, эмбеддинги |
| `postgres` + pgvector | справочник КТРУ, датасет, эмбеддинги (HNSW), результаты проверок |
| `redis` | кэш вызовов LLM и эмбеддингов, состояние пошагового сужения |
| `ollama` | локальная LLM (извлечение в JSON по схеме, тексты обоснований) и модель эмбеддингов; по умолчанию лёгкие `qwen3:4b` и `bge-m3`, выбор подтверждаем замером задержки |
| `web` (React + Vite + TS) | интерфейс |
